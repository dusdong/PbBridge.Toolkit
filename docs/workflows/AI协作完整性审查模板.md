# AI 协作完整性审查模板

本文档中的内容，就是放在 `docs\使用手册` 目录中的 **审查模板文档**。

它**不是给本仓库直接加载使用的项目级 skill 资产**，而是：

- 作为手册的一部分保存
- 供其他项目阅读、复制、裁剪和引用
- 作为“如何为自己的项目定义一个面向 Codex / GitHub Copilot 的完整性审查模板”的参考实现

也就是说：

- 本仓库把它放在 `docs/使用手册/` 下，当作文档使用
- 其他项目如果需要，可以把下面的 skill 正文复制到自己的 `.github/skills/`、`.codex/skills/` 或其他约定目录中使用

> 这是“写在手册里的审查模板”，不是“已经在本项目中启用的 skill”。

## 1. 适合什么项目引用

这个审查模板适合以下项目：

- 需要和 Codex / GitHub Copilot 协作的遗留系统项目
- 需要回答“真实 PowerBuilder 项目如何借助 `PbBridge.Cli` 让 Codex 参与编码”的项目
- 需要审查“系统是否已经足以支撑 AI 协作”的项目
- 需要把“已齐全 / 原型 / 不应承诺”三层判断写成固定审查流程的项目
- 希望避免把“已有命令”误写成“已经成熟产品能力”的项目

## 2. 使用建议

如果你要在**其他项目**中落地这个模板，推荐步骤是：

1. 先根据目标项目的真实文档、脚本、测试、任务与目录结构改写证据源
2. 再调整“已齐全 / 原型 / 不齐全”的判断标准
3. 最后再复制到目标项目自己的 skill 目录

不建议直接原样照搬，因为不同项目的：

- 技术栈
- 任务入口
- 文档结构
- 测试基线
- 平台边界

通常都不一样。

## 4. Skill 正文（供其他项目复制）

下面给出可供其他项目复制和改写的 `SKILL.md` 正文：

```md
---
name: codex-copilot-completeness-review
description: 从 Codex / GitHub Copilot 的协作视角，审查当前工作区是否已具备 AI 协作前置层所需的关键能力，并给出基于证据的齐全度结论与缺口清单。
---

从 **Codex / GitHub Copilot 协作视角** 审查当前工作区是否已具备目标系统作为“AI 协作前置层”所需的关键能力。

**输入**：可选指定审查目标口径。如果用户没有明确说明，你必须先区分下列两种目标：

- `让真实 PowerBuilder 项目先经由 PbBridge.Cli 转成 Codex 可处理的文本工作区`
- `辅助开发工具 / AI 协作前置层`
- `成熟的生产级双向桥接系统（或等价的最终产品目标）`

如果用户只说“功能是否齐全”，你**不能**直接给出单层结论；必须同时输出两层判断。

**步骤**

1. **先明确审查口径**

   如果用户没有显式说明目标，先确认本次审查是否聚焦：

   - “是否足够支撑 Codex / Copilot 在文本层协作”
   - “是否已经达到生产级产品成熟度”

   **重要提示**：
   - 不要把这两个问题混为一谈
   - 不要自动把“有命令 / 有入口 / 有原型”解释成“已经成熟可承诺”

2. **收集主证据源**

   优先读取并交叉比对以下内容：

   - 项目进度文档
   - 用户使用手册 / 边界说明
   - 工作区任务定义
   - 推荐脚本
   - 主实现目录
   - 测试目录
   - 宿主或 UI 集成目录

   如果某些文档缺失，允许降级为代码与测试证据，但必须在最终报告中注明“证据源缺失”。

3. **建立审查维度**

   至少按以下维度盘点能力：

   - **AI 可读性**：是否能把原始资产转为 Codex / Copilot 可处理的文本产物
   - **结构化证据**：是否能提供 manifest、verify、diff、report 等可审查产物
   - **人工导航与宿主消费**：宿主或 UI 是否支持浏览、对象打开、问题消费、报告打开
   - **自动化入口**：是否有稳定的任务、脚本、基线检查和诊断入口
   - **写回安全性**：导入/回滚/应用能力是否仍属于原型，是否具备成熟承诺条件
   - **平台与版本边界**：是否清楚限定目标版本、平台和受限适配器范围

4. **按成熟度做三层分类**

   对每个关键能力，必须分类为以下三档之一：

   - **已齐全 / 可直接用于 Codex-Copilot 协作**
   - **已有能力但仍偏原型 / 仅适合预演与内部验证**
   - **当前不齐全 / 不应对外承诺**

5. **审查 Codex / Copilot 的实际可用性**

   从 AI 协作角度重点回答：

   - 对于真实 PowerBuilder 项目，是否已经具备让 Codex 进入文本层编码所需的前置条件
   - Copilot 是否已拥有足够好的文本输入面
   - Codex 是否已拥有足够好的批量任务证据链
   - 用户是否已有稳定入口把 AI 建议落回到“可审查、可复核”的流程里
   - 当前是否缺少会显著影响协作体验的关键环节，例如即时反馈、轻量摘要、导航能力、风险说明

6. **输出风险分级**

   至少按 `高 / 中 / 低` 给出风险分级，并说明：

   - 为什么它是风险
   - 它影响的是“AI 协作效率”还是“写回安全性”
   - 它是否阻止当前系统被称为“辅助开发工具 / AI 协作前置层”

7. **给出最终双层结论**

   最终报告必须同时回答：

   1. **对“辅助开发工具 / AI 协作前置层”是否齐全？**
   2. **对“成熟的生产级双向桥接层”是否齐全？**

   推荐口径：
   - 第一层通常是“**基本齐全，但有边界**”
   - 第二层通常是“**尚不齐全，不应过度承诺**”

8. **生成审查报告**

   使用清晰 Markdown，至少包含：

   - `## 审查结论`
   - `## 已齐全能力`
   - `## 已有但仍偏原型的能力`
   - `## 当前不齐全/不应承诺的能力`
   - `## 风险分级`
   - `## 推荐外部表述`

**优雅降级**

- 如果没有完整用户文档：继续使用进度文档 + 代码 + 测试 + 任务定义进行判断
- 如果没有任务定义：改为从脚本和 README 寻找自动化入口
- 如果没有写回相关证据：不要直接判定为“齐全”，应降为“证据不足或仍处原型阶段”

**输出格式**

- 先给双层结论，再展开细节
- 用项目符号或表格区分能力层级
- 风险项按 `高 / 中 / 低` 分组
- 引用文件路径时使用反引号
- 不要输出含糊结论，例如“看起来差不多齐了”
```

## 5. 给其他项目的引用建议

如果其他项目要引用本模板，建议至少同时准备：

- 该项目自己的进度文档
- 该项目自己的使用手册或边界说明
- 该项目自己的任务 / 脚本入口
- 可证明“当前能力状态”的测试或验证结果

否则，这个 skill 很容易退化成“格式很好看，但结论没有证据支撑”的空模板。
