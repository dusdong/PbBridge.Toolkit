# PbBridge v4 写回契约参考（历史归档）

> V4 不再是当前 delivery 事实源。当前流程必须重新运行 V6 DryRun，禁止把本文描述的旧结果映射为 V6。

v4 import/writeback JSON 使用 `pbbridge-v4-*` 和 `schemaVersion=4`。顶层 `status` 只允许 `applied|noop|blocked|failed|argument-error`。

- `applied`：真实 PBL 写回成功，且 `writebackVerdict=applied`、`pblWritebackCount > 0`。
- `noop`：DryRun、未请求写回或无变化。
- `blocked`：预检阻断，例如缺 PBT 编译依赖、PBL 文件锁、人工计划缺少 `actionName`。
- `failed`：执行失败或写回失败。

`writebackVerdict` 必填：`not-requested|dryrun-only|applied|noop|blocked|failed|rolled-back|recovery-required`。

rollback 结果必须包含 `rollbackVerdict=not-needed|restored|partial|not-restored|manual-required`，摘要必须明确 PBL 已恢复、未恢复或需要人工处理。

新增对象使用 `pbbridge import source --source <sr-path> --target-pbl <pbl> --object-type <type> --object-name <name> [--apply] [--writeback] [--workspace <path>] [--workspace-name <name>] [--preflight-result <dryrun-json>]`。`--writeback` DryRun 会先把源码复制到项目根 `.pbbridge/local/staging/import/<sessionId>/`，再用 scratch PBL 执行导入/编译预检；缺写回适配器、PBL 文件锁、缺编译依赖或 PB 编译错误都会在 DryRun 阶段返回 `blocked`。

`import source` 的 `objectKey` 固定输出路径化形式：`<workspace-relative-pbl-path>:<object-type>:<object-name>`，例如 `pb-libs/Lib_Query.pbl:userobject:nvo_query`。manifest 是对象归属的唯一来源。

`--workspace` 可传项目根，也可传包含 `manifest.json` 的 state/artifacts 根。`4.0.1` 起，项目根会按 `--workspace-name`（默认 `default`）定位 `.pbbridge/workspaces/<workspaceName>/artifacts/pbbridge/manifest.json`；找不到 manifest 且请求 `--writeback` 时，结果必须为 `blocked`，`failureCategory=manifest-required-for-pbt-context`。若 manifest 中有 `workspaceRoot`，相对 `compileLibraries[]` 一律按 `workspaceRoot` 解析；staging 仍固定在项目根，避免把业务源码或 artifacts 快照混作写回事实源。Apply 必须复用 DryRun facts；若 source hash、staging hash、target PBL hash、compile libraries hash 或 workspace/state root 漂移，结果必须为 `blocked`。

`4.0.1` 起，`pbbridge-v4-import-source` 顶层结果必须输出 `rollbackVerdict`；scratch preflight 生成诊断包时，顶层 `diagnosticsBundleJsonPath` 与 `preflight.diagnosticsBundleJsonPath` 保持一致，消费方优先读取顶层字段。

`4.1.0` 起，`pbbridge-v4-import-source` 还必须输出 v4 `preflightSummary`、`rawPreflightResultJsonPath`、`targetPblRiskVerdict`、`scratchRecoveryVerdict`、`pbCompileFailureCategory`、`pbCompileFailureConfidence` 和 `ideFallbackRecommended`。当前结果排障优先运行 `pbbridge diagnostics summary --result <json>`，该命令只聚焦传入结果及其 diagnostics bundle，不从项目级旧状态推断写回结论。

`4.2.0` 起，v4 import/writeback 结果还必须输出 `sourcePreflightSummary`、`sourceDiagnostics[]`、`compileContextSummary`、`reExportReviewSummary` 和 `ideValidationVerdict`。`sourceDiagnostics[]` 必须能定位对象、源文件、行号范围、片段摘要、分类、置信度和建议动作；分类固定为 `source-syntax|encoding|datawindow-syntax|dependency|target-pbl|pbspy-pbsdk-limitation|ide-fallback-required|unknown`。`compileContextSummary` 必须结构化列出 PBW/PBT 来源、LibList、目标 PBL、只读 PBL/PBD、staged PBL、副本路径、PBD/native 原路径和缺失依赖。Apply 成功后默认 `ideValidationVerdict=required`，表示 PBL 已写入但 PowerBuilder IDE Regenerate / Full Build / 运行验收尚未完成。

`4.3.0` 起，v4 import/writeback 结果必须输出 `targetObjectWritebackVerdict=not-written|written-matches-source|written-differs|written-unverified|unknown-risk`、`writeBackAppliedState=none|applied|partial|unknown`、`targetPblChanged`、`targetPblHashBefore/After`、`importVerdict`、`compileVerdict`、`reExportReviewVerdict`、`driftClassification[]`、`compileContextRecommendation`、`missingTypeHints[]` 和 `dependencyResolutionHints[]`。DryRun full JSON 必须能直接作为 Apply 的 `--preflight-result`；高层 `writeback object` 外层 DryRun 会跟随 `importResultJsonPath` 到底层 import-source facts；compact summary 仅用于 stdout，若传给 Apply 必须包含可跟随的 `resultJsonPath`。二次重发后，Apply 只读取 DryRun JSON 中的必要 facts，历史 full JSON 的无关字段形态不兼容时应返回 v4 可诊断错误或继续使用 `sourceFactSet`，不得泄漏 Object/Array 底层异常。推荐高层入口为 `pbbridge writeback object <workspace-relative-pbl-path>:<object-type>:<object-name> --source <sr-path>`。

`4.3.1` 起，`writeback object --apply --preflight-result <writeback-object-dryrun.json>` 必须按 facts-only 方式读取外层结果并跟随 `importResultJsonPath`，底层 `import-source/import-object/import-objects` Apply drift guard 只消费 `sourceFactSet` 必要事实。数组根、schema mismatch、compact summary 缺路径或旧字段形态不兼容必须返回 v4 可诊断错误，不得泄漏 `.NET JsonElement Object/Array` 异常。PBL 被触碰后，高层结果必须尝试对象级 recover/re-export；反导与源码一致时应输出 `status=applied`、`writebackVerdict=applied`、`targetObjectWritebackVerdict=written-matches-source` 和 `pblWritebackCount>0`。

`writeback object` 顶层必须明确 preflight 和 recover 事实：`preflightResultAccepted` 表示是否接收了外部 `--preflight-result`，`preflightFactsSource=writeback-object|import-source|none` 表示采用外层高层 DryRun、底层 import-source DryRun 或未采用外部 facts，`preflightFactsPath` 指向实际被接受的 facts JSON。`recoverVerdict=not-needed|succeeded|failed|partial`、`recoverReason=apply-exception|post-review-failed|verification-failed|null`、`recoveredObjectMatchesSource` 和 `recoveredIssues[]` 用于表达主流程异常后的恢复结论。`recoveredIssues[]` 只能包含业务级 issue；若底层出现 Object/Array 形态异常，code 使用 `PREVIOUS_RESULT_SHAPE_INCOMPATIBLE` 或 `IMPORT_APPLY_INTERNAL_RESULT_SHAPE_MISMATCH`，诊断细节放入 `details.jsonPath`、`details.expectedSchemaName`、`details.actualSchemaName`、`details.actualRootKind`、`details.recoverVerdict`、`details.recoverReason` 和 `details.recoveredObjectMatchesSource`。

调用方判断写回闭环时，优先使用对象级事实：`targetObjectWritebackVerdict=written-matches-source` 且 `writebackVerdict=applied` 且 `pblWritebackCount>0` 表示对象已真实写入 PBL，Apply 原异常只作为 warning 事实保留。`targetPblChanged=true` 但对象未确认时必须输出 `targetObjectWritebackVerdict=written-unverified` 且 `pblWritebackCount=0`。`import-objects` 的 `pblWritebackCount` 按已确认匹配的对象数计数，不按底层 PBL 批次数计数。

`4.3.2` 起，`targetObjectWritebackVerdict` 新增成功类 `written-format-only-drift` 和失败类 `written-business-differs`。格式归一化只处理 CRLF/LF/CR、文件末尾换行和每行尾部空白；不归一化正文内部空白、成员顺序、属性值或 SQL 语义。规范化后一致继续输出 `written-matches-source`；仅格式差异输出 `status=applied`、`writebackVerdict=applied`、`targetObjectWritebackVerdict=written-format-only-drift`、`pblWritebackCount>0`，并保留 warning；业务差异输出 `written-business-differs`，不计入 `pblWritebackCount`。Apply 使用过期 DryRun 时，阻断 code 使用 `PREFLIGHT_FACTS_STALE`，compact summary 必须能直接看到漂移字段和“重新 DryRun”的下一步。`diagnostics summary --result <v4-json>` 会汇总对象写入、PBL 变化、反导 normalized diff 和 IDE Full Build 建议，避免调用方手工追多个 JSON。

`4.4.0` 起，新增高层闭环入口：

```powershell
pbbridge writeback close-loop --object <workspace-relative-pbl-path>:<object-type>:<object-name>[=<sourcePath>] [--apply] [--result <json>]
pbbridge writeback close-loop --object app.pbl:datawindow:d_order=src/d_order.srd --object app.pbl:window:w_order=src/w_order.srw --apply
```

未传 `--apply` 时只执行 source preflight、DryRun 和 close-loop plan，不写 PBL；传入 `--apply` 时在单命令内执行 DryRun、Apply、re-export、normalized diff 和 final verdict。v1 只允许同一目标 PBL；跨 PBL 输入返回 `argument-error`。多对象排序固定为 `structure -> function -> datawindow -> userobject -> window -> menu -> application -> other`，同类型保持用户输入顺序。

`pbbridge-v4-writeback-close-loop` 顶层必须输出 `closeLoopVerdict=dryrun-only|ready-for-ide-validation|ready-with-format-warnings|blocked|failed|business-differs|ide-fallback-required`、`requestedObjectCount`、`writtenObjectCount`、`sourceMatchesCount`、`formatOnlyDriftCount`、`businessDiffCount`、`blockingIssueCount`、`pblWritebackCount`、`requiresIdeFullBuild`、`deliverySummaryText` 和 `objects[]`。交付判断优先读取 `closeLoopVerdict`：`ready-for-ide-validation` 表示已写入且源码一致；`ready-with-format-warnings` 表示可进入 IDE Full Build 但需保留格式 warning；`business-differs` 表示不能交付，需要处理业务差异。

`4.4.1` 起，外部项目 `pbbridge-writeback-close-loop.ps1` 默认结果文件名固定为 `writeback-close-loop-{firstObjectShortName}-{hash16}.json`，避免多对象长路径触发 Windows 路径限制。PowerShell wrapper 的多对象参数必须使用 `-Object @("...","...")` 或 `-Objects @("...","...")`；CLI 原生命令仍使用重复 `--object`。`closeLoopVerdict=dryrun-only` 时，`blockingIssueCount` 只统计真实阻断 check，不把“等待确认 Apply”或 `not-written` 当作阻断。

`4.5.0` 起，DataWindow 对象在 close-loop DryRun/Apply 前会执行结构级 DataWindow validate。明确的 retrieve SQL 参数、arguments、select alias 与 column/dbname mismatch 会进入 `checks[].issues[]` 并阻断 Apply；`deliverySummaryText` 会包含 DataWindow 校验 issue 摘要。该校验不连接数据库、不校验 SQL 真实语义，也不生成 `.srd`。

`4.6.0` 起，`writeback close-loop` 默认启用本机 writeback session cache。命令新增 `--session <id>`、`--no-session-cache` 和 `--session-retention-days <n>`；未显式传入 session 时，CLI 按 workspace 与目标 PBL hash 生成本机 session。结果顶层必须输出 `sessionId`、`sessionCacheEnabled`、`sessionCacheStatus=created|hit|miss|stale|disabled`、`sessionCachePath`、`sessionCacheKey`、`reusedFacts[]`、`invalidatedFacts[]`、`cacheInvalidationReasons[]`、`cacheHits[]`、`cacheMisses[]` 和 `elapsedMs`；对象级结果输出 `sessionObjectCacheStatus`、`dataWindowValidateCacheStatus`、`dryRunElapsedMs`、`applyElapsedMs` 和 `reExportElapsedMs`。compact summary 必须保留 session cache 关键摘要。

`4.6.1` 起，自动 session 身份和同 PBL Apply lock 均基于目标 PBL 规范路径 hash，不再基于 PBL 内容 hash；PBL 内容 hash 只作为 cache key 与 stale guard 事实。DataWindow validate cache 按 `objectKey + sourceHash + strict + validatorVersion` 命中，命中时可复用只读 validate JSON，但 Apply 前仍必须重新计算当前源码 hash、目标 PBL hash、staging hash 和 stale guard。`session.json` 的 `results[]` 追加 `objectKeys[]`、`sourceMatchesCount`、`formatOnlyDriftCount`、`cacheStatus`、`cacheHits[]`、`cacheMisses[]`；`objects[]` 是 session 内按 `objectKey` 去重后的累计视图。`diagnostics summary --session` 必须从所有 result summary 重新计算聚合 verdict、写入数、源码一致数、格式差异数、业务差异数、阻断项和 cache 命中/未命中，不再信任旧 session 顶层 `aggregateVerdict` 或只读取当前 session cache 状态。旧 4.6.0 `session.json` 仍可读取，缺失的新字段按空值或旧字段 fallback 处理。

session cache 只复用 manifest parse、target resolution、library resolution、compile context、DataWindow validate 结果和 scratch/re-export workspace skeleton 这类本机只读事实或工作区准备。每次 Apply 前仍必须重新计算当前源码 hash、staging source hash、目标 PBL hash/timestamp、compile library file hash，并继续执行 v4 stale guard；cache hit 不得改变 `status`、`writebackVerdict`、`targetObjectWritebackVerdict`、`pblWritebackCount` 或退出码语义。若 workspaceRoot、stateRoot、manifestHash、compileLibrariesHash、sourceHash、targetPblHash、objectKey、actionName、sourceEncoding、driftPolicy 或 compileContextMode 漂移，结果必须标记 `sessionCacheStatus=stale` 并重新 DryRun，不得复用写回事实。

Apply 路径必须为同一目标 PBL 建立 `.pbbridge/local/locks/writeback-{targetPblPathHash16}.lock`。有效 lock 存在时返回 `status=blocked` 并输出 issue code `WRITEBACK_SESSION_LOCKED`；4.6.1 起 lock 文件写入唯一 token，持有文件句柄到 Apply 结束，释放时只删除 token 匹配的 lock。默认 2 小时以上且未被活动句柄持有的 stale lock 可自动替换并输出 warning。session index 写入使用 `.pbbridge/local/locks/writeback-session-{sessionIdHash16}.lock` 串行保护 `session.json`、`context-snapshot.json` 和 cache 写入；如果 session index 因 IO、权限或 JSON 读取问题更新失败，主 close-loop 交付结论不改判，只追加 warning issue `WRITEBACK_SESSION_INDEX_UPDATE_FAILED`。如果该 warning 追加后重写主 result JSON 仍失败，返回结果追加 `WRITEBACK_SESSION_WARNING_PERSIST_FAILED`，提示磁盘 result JSON 可能缺少这条 warning。该 lock 只保护本机并发 Apply/session index，不替代 Git/submodule/PBL 文件锁治理。

新增 session 管理入口：

pbbridge writeback session list [--workspace <path>] [--workspace-name <name>] [--result <path>]
pbbridge writeback session prune --older-than <days> [--workspace <path>] [--workspace-name <name>] [--result <path>]

`diagnostics summary --session` 继续输出 `pbbridge-v4-diagnostics-summary`，并新增 `sessionId`、`sessionResultCount`、`sessionObjectCount`、`sessionWrittenObjectCount`、`sessionBusinessDiffCount`、`sessionBlockingIssueCount`、`sessionCacheHitCount`、`sessionCacheMissCount` 和 `sessionAggregateVerdict`。session 聚合 verdict 优先级为 `blocked > business-differs > ready-with-format-warnings > ready-for-ide-validation > dryrun-only`。如果 `session.json` 损坏，`writeback session list` 将该 session 标记为 `unreadable`，`diagnostics summary --session` 返回 blocked 并输出 `WRITEBACK_SESSION_INDEX_UNREADABLE`，不泄漏底层 JSON 解析异常。`writeback session prune` 只清理 `.pbbridge/local/` 下的 session/cache/lock 元数据，不删除业务源码、PBL、manifest 正式产物或用户显式保存的 result JSON；即使 `--older-than 0`，也不得删除未超过内部 stale lock 阈值的 active lock。

所有 PB Bridge JSON 产物通过统一原子写入路径落盘：先写同目录临时文件，序列化和 flush 成功后再替换目标文件；失败时尽力删除临时文件，避免调用方读到半截 result、session、cache 或 diagnostics JSON。fallback 覆盖路径不得先删除旧目标文件，替换失败时应尽量保留旧 JSON 可读。

## SourceFactSet 最终形态

`4.0.0` 最终契约不保留 legacy import/writeback fact path。`import source`、`import-object` 和 `import-objects` 必须先构建 `SourceFactSet`，再由 adapter 生成 diff、plan、target batch、DryRun preflight 和 Apply 输入。

顶层结果必须包含 `sourceFactSet`。每个 fact 至少表达：

1. `objectKey`：路径化格式 `<workspace-relative-pbl-path>:<object-type>:<object-name>`。
2. `actionName`：只允许 `add|modify|delete|noop`，人工计划或结果中不得只出现数字 action。
3. `sourcePath`、`sourceHash`、`stagingSourcePath`、`stagingSourceHash`：`delete/noop` 场景可以没有 staging source，但必须显式输出 null，而不是改读 artifacts checksum。
4. `targetPblPath`、`targetPblHash`、`compileLibraries`、`compileLibrariesHash`。
5. `manifestEntry`、`currentEntry`、`baselineEntry`、`sourceRelativePath`、`factHash`。

`objectResults[]` 不再作为私有 `ObjectFact` 决策源；每个对象结果只能引用对应 `sourceFactSet.facts[]` 的 `objectKey/actionName/sourceHash/stagingSourceHash/targetPblPath/targetPblHash`。批量对象的 `sourceFactSet.facts[]` 顺序必须与规范化后的 `objectKeys[]` 一致，重复 key 必须返回 `argument-error`。

Apply drift guard 统一比较 SourceFactSet：`sourceHash`、`stagingSourceHash`、`targetPblHash`、`compileLibrariesHash`、workspace/state root、`actionName` 和 `objectKey` 任一漂移都必须 `blocked`，不得回退到旧 `resolvedSourceHash`、`ObjectFact`、manifest-only 私有事实或对象级私有 drift 比较。

## 发布前收口语义

`schema show`、command descriptor 与 `contract validate <json>` 同时覆盖 v3 只读契约和 v4 import/writeback 契约；`contract validate` 仍只接受位置参数 JSON 文件路径，不新增 `--input`。

写回管线统一使用 `.pbbridge/local/staging/import/<sessionId>/`。业务源码文件不会被 PBSpy/PBSDK 直接读取；非目标 `.pbl` 编译依赖会复制到 staging 的 `libs` 子目录，目标 PBL 继续使用真实路径，`.pbd/native` 依赖保留原路径，scratch PBL 不再二次 staging。

成功 Apply 后，结果可追加 `evidenceSupersession`，并写出 `.pbbridge/evidence-supersession/<target-pbl>-<object-key-hash>.json`。该 sidecar 只标记同一 `targetPblPath + objectKey` 下旧 `failed/blocked/rolled-back` 证据已被当前成功写回取代；旧 JSON 不会原地改写。

`.pbbridge/local/staging/import` 与 `.pbbridge/local/scratch-preflight` 属于 local-only 运行证据，默认保留以便审计。`diagnostics summary` 发现 session 超过 20 个或最旧超过 7 天时只输出 warning，不阻断 DryRun/Apply；发布前可人工清理。

真实外部项目收口采用只读证据：例如 `G:\Langchao\国润铜业\.pbbridge\v4-closure-external-dirty-evidence.json` 记录 root/pb-libs Git 状态、目标 PBL 最新 hash、非目标 compile PBL hash/length 对比。该证据用于说明旧 runtime 曾触碰共享库 PBL，而最终补丁后的 DryRun/Apply 未再改变非目标 PBL；生成该文件不执行新的 PBL 写回，也不还原历史脏状态。
