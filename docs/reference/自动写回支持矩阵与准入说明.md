# 自动写回支持矩阵与准入说明

本文档回答一个更具体的问题：

> `autonomous-writeback` 什么时候可以用，什么时候必须阻断？

先给结论：

> 当前自动写回已经有**生产强化后的受控闭环**，但只在**支持矩阵成立、项目进入 allowlist、持有安全来源的执行令牌、风险等级不超阈值**时才允许继续。

补充边界：

> 日常 Codex 开发使用 `PbBridge.Toolkit` 的主路径是 `.pbl → .sr* → Codex 修改 .sr* → import 回 .pbl`，编译、调试和运行验收由 PowerBuilder IDE 完成。本文描述的是更高等级的自动写回和生产托管门禁，不是 toolkit 日常开发可用性的前置条件。

`CompileEntryImport -11` 必须阻断当前 apply。该场景需要保留 PBSpy DryRun / Apply 证据；若 `doctor --adapter orca` 给出 PB9、PBSpy.dll、PBSDK、进程架构、编码模式和 final library list 等准入证据，可以尝试 `--adapter orca` 的 PBSpyORCA candidate 写回链路。已验证 x86 与 x64 行为一致时，进程架构只作为证据记录，不作为 candidate 准入硬门槛。candidate 仍失败时，才交由 PowerBuilder IDE 兜底；兜底后必须 re-export / verify / diff 或反向导出确认，并完成 PowerBuilder IDE Regenerate / Full Build。此规则不把 ORCA 设为全局默认写回器。

## 1. 当前支持等级

当前需要区分两套等级：

1. **运行支持等级**
   - `Unsupported`
   - `Experimental`
   - `LowRisk`
2. **自动写回认证等级**
   - `未认证`
   - `样板守线通过`
   - `真实项目认证通过`
   - `生产托管批准`

当前仓库已落地的是：

- **带硬失败准入的自动写回闭环**
- 面向 **allowlist 项目**
- 面向 **低风险或认证计划**
- 面向 **带审计包、带自动回滚、带恢复复核** 的受控执行

## 2. 当前门禁模型

自动写回必须同时通过四道门：

1. **策略门禁**
   - 工作区策略文件已启用自动写回
   - 工作区根路径在 `allowedWorkspaceRoots` 中
   - 当前对象类型、库范围、风险阈值符合策略
2. **执行授权**
   - 策略侧只能通过环境变量或受控文件记录预期令牌来源引用
   - 调用方优先通过 `--token-env` 或 `--token-file` 提供令牌；runtime transient `--token` 仅为兼容保留
3. **环境门禁**
   - 当前平台、架构、适配器命中支持矩阵
4. **执行后门禁**
   - apply 后 `re-export / verify / diff` 复核通过
   - 若失败则自动 rollback
   - rollback 后必须通过 recovery verify

## 3. 工作区策略文件

当前策略文件仍然放在：

- `artifacts/pbbridge/pblbridge.json`

其中自动写回部分的核心字段包括：

- `enabled`
- `supportMatrix.supportLevel`
- `supportMatrix.supportedPlatforms`
- `supportMatrix.supportedArchitectures`
- `supportMatrix.supportedAdapters`
- `allowedWorkspaceRoots`
- `allowedLibraries`
- `allowedObjectTypes`
- `maxRiskLevel`
- `allowSignatureChanges`
- `allowDeleteActions`
- `allowCrossLibraryChanges`
- `allowForceApplyOnConflicts`
- `requireExecutionToken`
- `executionTokenReference`
- `certificationStatus`
- `maxVerifyErrorCount`
- `maxVerifyWarningCount`

一句话理解：

> **没有策略文件，就没有自动写回；策略没显式放行，就默认阻断。**

`requiredExecutionToken` 仅在迁移窗口内保留读取形状，不再是可配置能力，也不再参与授权。任何当前消费入口检测到非空旧字段时都会以唯一原因码 `PBA104` 失败关闭，并在读取令牌来源、Doctor、freshness 或创建 result/audit 前停止。请显式迁移：

```bash
dotnet run --project src/PbBridge.Cli -- autonomous-policy-template <workspacePath> --policy <configJsonPath> --enable --token-env PBBRIDGE_AUTONOMOUS_TOKEN
```

也可以把最后一项改为 `--token-file <tokenFilePath>`。迁移只写入来源引用并删除旧字段；不会读取、复制、备份或转存旧明文，也不会自动创建环境变量或 secret 文件。

`autonomous-policy-template --token ...` 已退役，无论 flat 还是 `autonomous policy-template` grouped form，都会在配置读取和文件/目录副作用前返回 `INVALID_ARGUMENT`。这与读取旧策略后的 `PBA104`/blocked 是两条不同失败通道。

当前策略模板还有两个新特征：

- 如果启用 `--capture-verify-thresholds` 但基线输出缺少 `manifest.json`，策略生成会直接失败
- 如果当前项目已经有导出产物，策略模板会自动收紧 `allowedLibraries / allowedObjectTypes`，不再默认“空即全放行”

## 4. 当前推荐准入流程

建议把项目准入固定成下面这条流程：

1. 用 `autonomous-policy-template` 生成或刷新 `pblbridge.json`
2. 显式确认 `allowedWorkspaceRoots / allowedLibraries / allowedObjectTypes`
3. 用 `autonomous-admission-check` 先做准入检查
4. 用 `autonomous-release-gate` 或发布门禁脚本跑一遍 no-op 守线
5. 如需申请更高承诺，再用认证模式执行真实变更认证
6. 认证成功后，生成标准认证包
7. 通过后，再逐步扩大对象范围

推荐命令：

```bash
dotnet run --project src/PbBridge.Cli -- autonomous-policy-template <workspacePath> --enable --token-env PBBRIDGE_AUTONOMOUS_TOKEN
```

```bash
dotnet run --project src/PbBridge.Cli -- autonomous-admission-check <workspacePath> <outputPath> --policy <configJsonPath> --token-file <tokenFilePath>
```

```bash
dotnet run --project src/PbBridge.Cli -- autonomous-release-gate <workspacePath> <outputPath> --policy <configJsonPath> --token-env PBBRIDGE_AUTONOMOUS_TOKEN
```

如果你要把当前输出直接固化为真实项目的 verify 基线，可以这样做：

```bash
dotnet run --project src/PbBridge.Cli -- autonomous-policy-template <workspacePath> --policy <configJsonPath> --enable --token-env PBBRIDGE_AUTONOMOUS_TOKEN --baseline-output <outputPath> --capture-verify-thresholds
```

其中：

- `autonomous-policy-template` 会自动填充当前平台、架构和可用适配器
- `autonomous-policy-template` 会在基线证据缺失时直接失败
- 若使用 `--token-env / --token-file`，策略会记录令牌来源引用而不是回写明文令牌
- admission、release gate、writeback、兼容 import 与 V8 `ApplyIfEligible` 统一由同一个 canonical policy evaluator 裁决
- `autonomous-admission-check` 只做准入评估，不会触发真实写回
- `autonomous-release-gate` 会在准入通过后继续跑一遍 no-op 自动写回守线，并可通过 `--cert-source-output` 进入真实变更认证模式
- 若本次运行要直接作为“生产托管判定”，应显式加上 `--require-production-approval`，此时退出码和最终结论都以 `productionGatePassed` 为准

真实变更认证完成后，推荐立即生成认证包：

```powershell
powershell -File scripts/rebuild-autonomous-certification-package.ps1 `
  -ProjectName <projectName> `
  -ReleaseGateJsonPath <releaseGateJsonPath> `
  -PolicyJsonPath <configJsonPath> `
  -AdmissionJsonPath <admissionJsonPath> `
  -CertificationJsonPath <certificationJsonPath> `
  -Owner <owner> `
  -Approver <approver> `
  -CertificationConclusion <conclusion> `
  -OutputPackagePath <outputPackagePath>
```

生成后的 `certification-package.json` 现在还会固定记录：

- `certificationSourceOutputPath`
- `certificationResultJsonPath`
- `releaseGateResultJsonPath`
- `certificationRunId`
- `certificationVerdict`

一旦认证包进入发布或真实项目守线流程，应把它视为**只读证据**：

- `build-release-engineering.ps1` 不会再隐式刷新认证包
- `check-real-project-production-guard.ps1` 的 `production` 模式也不会再隐式刷新认证包
- 如果认证结果发生变化，必须先单独执行 `rebuild-autonomous-certification-package.ps1` 更新 package，再由发布或守线流程消费

也可以直接使用发布门禁脚本：

```powershell
powershell -File scripts/check-autonomous-writeback-gate.ps1 -WorkspacePath <workspacePath> -PolicyPath <configJsonPath> -ExecutionTokenEnvVar PBBRIDGE_AUTONOMOUS_TOKEN
```

## 5. 对 `PB90` 样本的建议

`PB90` 最小样本更适合做：

- no-op 准入基线
- 低风险守线测试
- `run-id / audit directory` 审计结构检查

不建议把它一开始就当成：

- 高风险对象自动改写样本
- 默认 force-apply 样本

## 6. 对 `GuoRun / 国兴 / 国润铜业` 这类真实项目的建议

真实项目应按更保守的节奏推进：

1. 先完成导出、verify、report 基线
2. 把项目目录加入 `allowedWorkspaceRoots`
3. 先跑 **同源同目标的 no-op 自动写回**
4. 再跑低风险计划
5. 再申请认证模式
6. 认证成功后固化标准认证包
7. 最后才考虑更广对象范围

推荐优先纳入 allowlist 的对象包括：

- function
- structure
- 无签名变化的低风险 update

默认不应直接放开的对象或动作包括：

- delete
- signature change
- cross-library 变更
- conflict 下的 `forceapply`

## 7. 审计目录

每次自动写回都会生成：

- `artifacts/pbbridge/autonomous-runs/<run-id>/`

当前审计目录至少会包含：

- `policy.json`
- `doctor.json`
- `pre-verify.json`
- `pre-diff.json`
- `plan.json`
- `conflict.json`
- `import.json`
- `re-export/`
- `post-verify.json`
- `post-diff.json`
- `rollback.json`（若触发）
- `recovery-verify`（由 rollback 结果引用）
- `final-result.json`

## 8. 准入检查结果

`autonomous-admission-check` 当前会输出结构化结果，至少包含：

- `verdict`
- `isAdmitted`
- `supportLevel`
- `verifyErrorCount / verifyWarningCount / verifyInfoCount`
- `blockReasons`
- `suggestedNextStep`

推荐把这份结果直接纳入：

- allowlist 审核附件
- 真实项目试点记录
- 发布前守线证据

`autonomous-release-gate` 则会进一步汇总：

- `admissionResultJsonPath`
- `noOpWritebackResultJsonPath`
- `certificationWritebackResultJsonPath`（若启用认证）
- `gatePassed`
- `productionGatePassed`
- `certificationStatus`
- `verdict`

一句话理解：

> `admission-check` 解决“能不能进场”，`release-gate` 解决“这条路是否稳定”，`productionGatePassed` 才解决“能不能作为真实项目进入生产托管发布”。

> 如果调用方只看退出码，而不是读取 JSON 结果，那么只有在显式使用 `--require-production-approval` 时，`autonomous-release-gate` 的退出码才会严格代表“生产托管通过 / 未通过”。

> 发布工程如果要把生产托管门禁真正接进发版，还必须提供认证包，并由脚本从显式参数或认证包索引中解析 `certificationSourceOutputPath`；缺少认证输入时会直接阻断。

> 发布与守线现在都会直接校验**既有认证包**是否与当前 `release-gate` 结果强绑定；它们不会再通过“先刷新 package 再校验”来掩盖不一致。

当前 Windows CI 也已经把 `PB90` 的 `release-gate` 纳入持续守线，避免该能力只在本地偶然成立。

保留的 runtime 调用路径仍接受 transient inline token，但它可能暴露在 shell history、进程参数或 CI 日志中，因此不推荐用于生产。该兼容不允许把 inline 值写入策略、result、progress 或 audit；生产自动化应把 CI Secret 投影为环境变量或受控文件后再传入。

## 9. 当前不应承诺什么

当前不应对外写成：

- 所有真实 PB 项目都已支持 Codex 自动写回
- 当前默认允许 `forceapply`
- 当前已经具备无条件成熟生产承诺

当前可以更准确地写成：

> 当前系统已具备受门禁控制、带硬失败准入和非零退出码的自动写回闭环，可在 allowlist 项目、安全来源执行令牌和低风险策略下运行，并提供 apply 后自动复核、失败自动回滚、rollback recovery 复核与 run-id 审计包。

如果你要把某个真实项目从“试点可用”推进到“生产认证候选”，当前最小闭环应当是：

1. `admission-check` 通过
2. `release-gate` 通过
3. 真实变更 `certification` 通过
4. 生成标准认证包并送审
5. `productionGatePassed = true`
