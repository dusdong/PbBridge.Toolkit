# 业务变更交付视图（7.7.0）

`delivery summary --change-file` 只读汇总一个 workspace 中明确声明的对象与 session。它不调用 PB9、不执行恢复、不重新预检，也不写入 session、locator、锁或中间 summary。默认输出 stdout；显式 `--result` 只在既存独立目录中新建 JSON，已有文件、输入别名及受管位置均拒绝。

清单示例（源码相对 repo root，历史文件相对清单目录）：

```json
{
  "schemaName": "pbbridge-delivery-change-request",
  "schemaVersion": 1,
  "changeId": "order-adjustment",
  "title": "订单调整",
  "workspaceId": "default",
  "objects": [
    {"objectKey": "app.pbl:userobject:n_order", "sourcePath": "src/app/userobject/n_order.sru"},
    {"objectKey": "ui.pbl:window:w_order", "sourcePath": "src/ui/window/w_order.srw"}
  ],
  "currentSessionIds": ["<原交付session>", "<后续修复session>"],
  "historicalSessionFiles": []
}
```

```powershell
pbbridge delivery summary --repo-root C:\project --workspace default --change-file .pbbridge\local\task\change.json
pbbridge delivery summary --repo-root C:\project --workspace default --change-file .pbbridge\local\task\change.json --result .pbbridge\local\task\report-01.json
```

`--change-file` 与 `--session`、`--compare-summary` 互斥。相同对象和来源去重；冲突源码或目标映射、跨 workspace、非当前 session 与无效 schema 拒绝。来源文件无法取得时报告不完整；查询不扫描其他 session，也不把已有 summary 当事实源。各文件独立取得一致快照并保留 Hash，不承诺跨文件的全局事务快照。

业务视图必须有合法的当前 project/workspace 配置及 manifest；对象键与源码路径必须精确对应所选 manifest 中的受管对象。空目录、未配置 workspace、未知对象、冲突 manifest 映射、错误源码路径和源码链接别名均拒绝。合法受管对象尚无 session 时保留 unknown 和待办。此检查只读配置及 manifest，不执行同步、预检、PB9 或恢复。

报告为 `pbbridge-delivery-change-summary` / schemaVersion=1 / canContinue=false。`objectCount` 是唯一对象数，`verifiedWritebackCount` 是原证据核验的实际写回次数。每个对象分别显示 `latestAttempt`、`lastVerifiedWriteback`、`orderingAmbiguous`、`applicability`、`coverage` 和 `nextActions`。排序依据原执行时间，无法确定时保留歧义。

重复引用或不同 delivery 快照指向同一 intent/目标前后身份和对象时，只计一次物理写回；逐对象 attempts 使用相同去重规则。completion 的时间和 candidate 事实均来自本次已核验的缓存快照，不再次从磁盘拼接时间。readerBuildIdentity 复用构建身份 resolver；无法证明的字段为 unavailable，并在 readerIdentityReasonCodes 中说明。dotnet 宿主 Hash 不作为 CLI 身份，原 session producer 保持独立。

`applicability=matched` 只证明本次观察的源码、目标和依赖绑定匹配；同库后续写入须有连续 promotion/candidate 证据且对象语义未变。源码或依赖确认漂移为 stale，文件不可读、链断或恢复责任未解除为 unknown。查询不通过重新反导或 Apply 补造证明。

`sessionAcceptance[]` 原样展示 `recordedCoverage`、`recordedReadiness`、哈希核验的证据引用和原下一步。`relatedObjectKeys` 仅为导航。现有 attest 没有逐对象/验收时内容绑定，因此 `scopeBinding=unbound`、`currentApplicability=unknown`；单对象、note 只提 A、当前源码碰巧相同或工具 verified 均不推导对象验收。对象 runtime/business 等保持 not-checked，不跨 session 合成 release-ready。

`remainingAcceptance` 区分 not-checked、failed、coverage-binding-unconfirmed。已记录 attested 不因缺少绑定改成失败。先核对原验收范围；这不要求无变化重复 Apply 或重跑全部验收。对象仍匹配而最新尝试失败时，两条事实同时保留，按原 session 处理失败。

`nextActions` 与 `remainingAcceptance` 是结构化待办：scope、reasonCode、objectKeys、sessionIds、evidencePaths 说明范围与依据，action 使用既有 type/name/displayText/command/arguments 格式。验收待办属于原 session 范围，不把 relatedObjectKeys 当作验收范围；scopedRecordedNextAction 保留原 session 的动作和范围。workspaceAssessments 对同步、源码 Git、PBL Git、发布均明确 not-evaluated，不能从对象 matched 推导这些操作已通过。

P03 正常入口验证使用合成 NVO/窗口：首次两对象写回成功；A 后续来源缺失失败，再修复成功；最后 A 写回而 B 原生编译失败。最终为 2 个唯一对象、4 次实际写回，B 同时保留最新失败和上次成功。同 session 正常 attest 的 note 仅描述 A，原 runtime=attested，但 A/B 对象 runtime 均 not-checked。证据见 `.pbbridge/local/task-packages/PB770-20261103/P03`；这是开发 CLI 验证，不代表 AOT、完整发行、PB IDE 或业务人工验收。
