# 7.7.2 模板迁移治理契约参考

本文描述 PbBridge 7.7.2 的模板迁移公共契约。它不修改当前 `pbbridge-v8-delivery` schemaVersion 8、PBL 写回策略或 PB9 支持矩阵。

## 1. 归属与双哈希

受管 PowerShell provenance 使用 schemaVersion 2，并为当前可重建模板记录：

- `rawSha256`：安装、回滚、漂移和完整性依据。
- `normalizedTextSha256`：只参与来源分类。
- `normalizationProfile=powershell-text-v1`：严格解码 UTF-8 及带 BOM 的 UTF-8/UTF-16/UTF-32，移除 BOM 表现差异并把 CRLF/CR 统一为 LF；保留其他空白、注释与最终换行。

无法安全解码时结果必须为 `normalization-unsupported`，只使用 raw hash，不得猜测 format variant。来源分类顺序固定为 `managed-current-exact`、`managed-known-exact`、`managed-known-format-variant`、`managed-modified`、`unmanaged`。

## 2. 可提交 migration policy

`.pbbridge/migration-policy.json` 使用 `pbbridge-template-migration-policy` schemaVersion 1。首版只允许 canonical 仓库相对文件路径的 `project-custom/preserve`：

```json
{
  "schemaName": "pbbridge-template-migration-policy",
  "schemaVersion": 1,
  "productVersion": "7.7.2",
  "files": [
    {
      "path": "scripts/move-pb-build-output.ps1",
      "ownership": "project-custom",
      "action": "preserve",
      "reason": "项目自定义 PowerBuilder 构建输出布局"
    }
  ]
}
```

policy 只声明长期归属，不能绕过 AST、共享 module、CLI 参数或推荐 wrapper help/smoke 兼容性检查。glob、目录豁免、路径越界、重复路径和模板覆盖动作必须拒绝。

## 3. Plan/Decide/Apply

```powershell
.\scripts\pbbridge-template-migrate.ps1 -Plan -WorkspaceId canyin
.\scripts\pbbridge-template-migrate.ps1 -Decide -PlanHash <hash> -DecisionPath scripts/move-pb-build-output.ps1 -Reason "已审阅并保留"
.\scripts\pbbridge-template-migrate.ps1 -Apply -ProjectRoot <repo> -ToolkitRoot <toolkit> -WorkspaceId canyin -PbwPath <pbw> -PlanHash <hash>
```

Plan 的 canonical `semanticPlan` 排除时间戳和本机绝对路径并生成稳定 `planHash`。Decide 首版只产生 `preserve-custom-and-continue`；相同决定幂等，冲突决定失败。Apply 在写入前重新验证源文件、配置、policy、provenance、目标模板、planHash 和 decision set；任何漂移都以零项目写入阻断。没有待决定文件时允许一次性 `-Apply`。

旧 `-AcceptReviewedCustomizations` 和 `.pbbridge/template-migration-ack.json` 不再具有兼容或放行语义。

`-OutputPath` 指定项目内的独立 `.json` 报告副本。可以新建普通文件，或刷新可读且可写的 JSON 对象，其中 `schemaName` 必须精确为 `pbbridge-v7-template-migration`，`schemaVersion` 必须为数值 `8`。同一路径可以用于不同的阶段或计划。支持的路径示例包括：

- `.pbbridge/local/migration-report.json`
- `.pbbridge/local/migrations/fixture-canyin-dryrun.json`
- `.pbbridge/local/results/7.5.0-controlled/canyin/apply.json`
- `.pbbridge/local/benchmark/fixture-run/migration-plan/strict/iteration-1.json`

项目与 workspace 配置、迁移策略、受管模板目标、Toolkit 安装目录、Git 管理目录、迁移总索引和事务目录均受保护。目录、链接路径以及其他类型的占用文件也会被拒绝。原路径不再满足条件时，请改用项目内新的独立 `.json` 路径，或省略 `-OutputPath`。省略路径时，Plan 和 Apply 在 `.pbbridge/local/migrations/results/` 生成报告，Decide 更新原事务并通过标准输出返回结果。

显式路径在首次迁移写入前校验，已有报告在预检时以读写方式打开并保持原字节。项目外路径返回 `migration-output-outside-project`，其他不合法目标返回 `migration-output-path-invalid`。如果初检时空闲的位置在执行期间被占用，或初检时可刷新的旧报告被替换为异类文件，导出失败并保留占用文件的原字节。已经执行的迁移以事务审计为准。

## 4. schemaVersion 8 审计

迁移完整结果使用 `schemaName=pbbridge-v7-template-migration`、`schemaVersion=8`、`productVersion=7.7.2`。Plan 与 decisions 分别使用 `pbbridge-v7-template-migration-plan` 和 `pbbridge-template-migration-decisions` schemaVersion 8。

本机审计位于 `.pbbridge/local/migrations/`，包含 `plan.json`、`decisions.json`、`result.json`、`index.json`、candidate manifest、recovery manifest、staging 和 backup。审计只记录路径、hash、分类、动作、兼容性和恢复证据，不得包含源码正文、diff 正文或密钥值。

typed outcome 包括 `awaiting-decisions`、`ready-to-apply`、`applied-with-preserved-customizations`、`blocked-incompatible-customization`、`rolled-back` 和 `recovery-required`；重复输入完成验证且无写入时可以返回 `no-change` 等价完成态。

有写入的 Apply 验证安装后，先在事务目录提交完整的 `result.json`，再清理 staging 和 backup。以迁移索引关联的事务为准，核对 `migrationId`、`planHash`、`phase=completed`、成功的 `outcome` 和 `transaction.installedValidated=true`：

若进程中断或报出 `migration-terminal-audit-commit-failed`，先保留整个事务目录，特别是 `recovery-manifest.json` 和 backup。这个错误可能发生在结果替换前，也可能发生在替换成功后的读回阶段。先重读该事务的 `result.json`，按上述条件核实身份和终态，再处理对应情况。

- **确认成功结果已提交。** 保留已安装文件，可按正常流程重新 Plan。若 `transaction.cleanupStatus` 为 `pending`，清理结果尚未写入审计。若为 `successful-transaction-retained`，查看 `transaction.cleanupError`。清理状态更新失败时，标准错误流会给出 `migration-terminal-audit-cleanup-update-failed`，上一份完整结果仍可查读。独立报告导出失败时也可用此事务结果确认安装。
- **确认成功结果未提交。** 例如，文件仍是本次事务的 Plan 结果，或目录可读且该结果文件确实不存在。若目标偏离原态，按完整恢复清单恢复。对原有文件，从备份恢复并核对原始 SHA-256。对原先不存在的路径，确认实际缺失。核实全部原态后重新 Plan。
- **仍无法判断。** 若无法读取或解析审计，或身份无法与本次事务对应，保留事务和现有目标字节，暂缓重试 Apply。先排查访问问题并核对索引、计划和恢复清单，等终态可确认后采取对应操作。
- **Apply 失败并自动回滚。** `rolled-back` 表示自动回滚确认了清单中的原始文件状态，可以在排查安装失败后重新 Plan。`recovery-required` 表示恢复尚未确认。保留清单和备份，查看 `rollback.errors` 和 `rollback.restoredFiles` 定位问题，按清单核对全部原始存在性及 SHA-256 后重新 Plan。

### Apply 候选的工作区诊断

Apply 使用配套 CLI 对 staging 执行 `workspace context`。成功时从 stdout 读取工作区身份、manifest 路径和选择来源。迁移模块将 stderr 诊断写入 verbose 流。

候选查询失败时，`manualMigrations` 的相应条目包含候选配置路径、字段和消息，并提供两个可直接读取的 CLI 字段。

- `cliExitCode` 是 CLI 的原始整数退出码。查询无法启动时为 `null`。
- `cliErrorCode` 来自非零退出时 stdout 错误对象中可解码、非空白的字符串 `errorCode`。无法取得时为 `null`。stdout 缺少可读错误说明且 stderr 有诊断时，`message` 包含 stderr 的诊断摘要。
- `code` 在 CLI 拒绝候选或无法启动时为 `workspace-context-resolver-rejected`。CLI 退出 `0` 时，stdout 无法解析或必需字段无法解码对应 `workspace-context-resolver-json-invalid`，身份或 manifest 证据无效对应 `workspace-context-resolver-evidence-invalid`。

例如，候选 workspace 的配置身份为 `wrong-workspace` 时，报告包含如下条目。示例中的 `<staging>` 代表该事务的候选目录。

```json
{
  "code": "workspace-context-resolver-rejected",
  "fieldPath": "workspace",
  "path": "<staging>/.pbbridge/workspaces/canyin/workspace.json",
  "line": null,
  "column": null,
  "message": "Core workspace resolver 拒绝候选配置：选择的 workspace 'canyin' 与配置身份 'wrong-workspace' 不一致。",
  "cliExitCode": 2,
  "cliErrorCode": "workspace-config-identity-mismatch"
}
```

这类失败的 Apply 报告使用 `failure.reasonCode=candidate-validation-failed`，`actualWrites` 为空数组，迁移入口退出码为 `11`。

## 5. 门禁消费

release-check、project-health 和 toolkit upgrade-check 只读核对当前产品版本、planHash、decisionSetHash、policy hash、candidate/raw hash、workspace、目标模板和 preserved 兼容性。有效决定只解决文件归属；`awaiting-decisions`、决定过期、hash 漂移、不兼容或恢复未完成继续阻断。旧 ack 最多产生迁移指引，不能改变 blocked 或 severity。

V5.0.0/V5.0.1 无 V7 配置可以作为受支持的 legacy-origin；其中仍保留的 3.7.4 官方资产只有在不可变 Toolkit Git provenance 命中时才作为受管旧版处理。V7.0.0 至 V7.3.1 配置由单一集合验证并可直接迁移到当前版本。V5 官方单文件迁移入口必须命中历史 Git provenance 后才能升级为当前双文件组，未知自定义继续阻断。

仅有既存业务脏状态时，upgrade-check 的完成度为 `complete`、顶层可以是 `warning`，默认退出 0；`--strict-git-hygiene` 只把 warning 映射为非零退出码，不改变 JSON 分类。

完整报告的 `performanceSummary.stageTimings` 在原有 `preflight` 前记录以下已执行的检查。每项的 `elapsedMs` 为非负整数毫秒，`status` 取自 `checks` 的同名项。

| `stage` | 计时范围 |
| --- | --- |
| `template-current-content` | 受管内容检查，包含配置解析、事实采集和结果核验。 |
| `toolkit-identity` | 升级检查直接执行的 Toolkit 身份解析。 |
| `toolkit-producer-build-identity` | 生产构建身份核验，包含该核验内部执行的 Toolkit 身份解析。 |

缺少 Toolkit 根目录的 `manifest.json` 时，生产构建身份核验未执行，报告仅记录另外两项新增计时。整体耗时读取 `performanceSummary.totalElapsedMs`。Git、wrapper 和本机目录卫生阶段可以重叠。
