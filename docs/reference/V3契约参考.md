# PbBridge v3 CLI 契约参考

本文是 schemaVersion 3 JSON 消费方、CI、PowerShell wrapper、Toolkit skill 和 SharpIDE 集成层的契约参考。当前维护结果继续使用 `pbbridge-v3-*` schemaName / `schemaVersion=3`，并独立声明 `productVersion=7.5.1`；这里的 v3 是契约版本，不是当前产品版本。`4.0.0` 起，本文只作为只读/维护 workflow 与历史 import/writeback 结果的参考；当前交付写回使用 V8 delivery。

## 1. 契约识别

所有 v3 workflow 结果必须使用：

1. `schemaName=pbbridge-v3-<workflow>`
2. `schemaVersion=3`

常见 workflow 名称：

| workflow | schemaName |
| --- | --- |
| `project-health` | `pbbridge-v3-project-health` |
| `release-check` | `pbbridge-v3-release-check` |
| `readonly-sync` | `pbbridge-v3-readonly-sync` |
| `readonly-sync-summary` | `pbbridge-v3-readonly-sync-summary` |
| `pbl-change-intake` | `pbbridge-v3-pbl-change-intake` |
| `pbl-drift-remediation` | `pbbridge-v3-pbl-drift-remediation` |
| `shared-library-writeback-check` | `pbbridge-v3-shared-library-writeback-check` |
| `precommit-summary` | `pbbridge-v3-precommit-summary` |
| `project-model` | `pbbridge-v3-project-model` |
| `project-adoption-check` | `pbbridge-v3-project-adoption-check` |
| `project-drift-check` | `pbbridge-v3-project-drift-check` |
| `writeback-readiness-check` | `pbbridge-v3-writeback-readiness-check` |
| `diagnostics-summary` | `pbbridge-v3-diagnostics-summary` |
| `diagnostics-bundle` | `pbbridge-v3-diagnostics-bundle` |
| `diagnostics-bundle-verify` | `pbbridge-v3-diagnostics-bundle-verify` |
| `release-engineering-summary` | `pbbridge-v3-release-engineering-summary` |
| `release-readiness-lint` | `pbbridge-v3-release-readiness-lint` |
| `import` | `pbbridge-v3-import` |
| `import-object` | `pbbridge-v3-import-object` |
| `import-objects` | `pbbridge-v3-import-objects` |
| `import-package` | `pbbridge-v3-import-package` |
| `confirm-object-writeback` | `pbbridge-v3-confirm-object-writeback` |
| error / argument error | `pbbridge-v3-error` |

`pbbridge-<workflow>`、2.x 旧 JSON 名称和旧输出形态不再是 v3 稳定契约。`4.0.0` 起，`import` / `import-object` / `import-objects` 的稳定消费契约已经迁移到 v4；上表中的 v3 import/writeback 仅用于历史证据排障。

对象意图命令组使用独立的轻量契约，不伪装成 v3 workflow：`object-find`、`object-export`、`object-repair`、`object-diff` 分别输出 `schemaName=pbbridge-object-find|pbbridge-object-export|pbbridge-object-repair|pbbridge-object-diff`、`schemaVersion=1`。它们仍通过 compact stdout 暴露 `resultJsonPath`；`object find` 的 compact stdout 还在顶层直接暴露 `cacheStatus` 和 `totalElapsedMs`，用于不用读取完整 JSON 也能判断索引命中来源和总耗时。完整 JSON 必须包含 `targetPblChanged=false`、`summaryText`、`performanceSummary`、必要的 `nextCommand` / `alternativeCommands[]` / `diagnosticFacts[]`。`performanceSummary` 包含 `totalElapsedMs`、`cacheStatus`、`cacheReason` 和 `stages[]`，用于判断对象定位、PBL 临时导出、DataWindow inspect 或语义比较哪个阶段较慢。可用 `pbbridge schema show object-export` 查看字段摘要；`object export` 的关键字段包括 `manifestStatus`、`exportedObjectCount`、`changedSourceFiles[]`、`unchangedSourceFiles[]`、`extractionMode`、`fidelity` 和 `sourceHash`。

真实运行效率 benchmark 使用独立 schemaVersion 2 契约：`pbbridge performance benchmark` 输出 `schemaName=pbbridge-runtime-benchmark`，默认写入 `.pbbridge/local/results/runtime-benchmark-*.json`。结果包含 product/run/profile/cache/dataset/baseline/budget identity、显式 `runnerIdentity`、三类 measurement semantics version、逐 iteration workload/counters、`metrics[]`、`reasonCodes[]`、`targetPblChanged=false` 和 `summaryText`；schemaVersion 1 或缺少显式 runner/workload/semantics identity 的旧 v2 基线必须 fail closed，禁止派生伪回归。

Delivery 性能矩阵覆盖 no-change、同一 PBL 32 对象、同 workspace 多 PBL 三类 workload；medium 多 PBL 为 2×16 对象，large 为 4×16 对象。Delivery iteration 直接消费 canonical `Resolution`、`Planning`、`Preflight`、`DependencyPlanning`、`DryRun`、`Finalization` 阶段以及 requested object、target PBL、batch、cache availability 事实；阶段 p95 标记为 `diagnosticOnly=true`，首轮不形成独立硬阈值。总耗时仍承担硬门禁：no-change 执行绝对与兼容相对门禁，same/multi-PBL 仅在 workload 与 runner identity 完全兼容时执行相对门禁；medium `toolkit-upgrade-check` 预算为 15,000ms，large 为 45,000ms。`small` 是 smoke，显式 `real` profile 仅产生 warning。Delivery 中间结果必须写入 workspace `ResultRoot`，不能写入通用 `.pbbridge/local/benchmark/`。

## 2. 共同字段

所有 v3 workflow 结果必须包含：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `schemaName` | string | `pbbridge-v3-*` 名称 |
| `schemaVersion` | number | 固定为 `3` |
| `generatedAt` | string | 结果生成时间 |
| `status` | string | `success`、`blocked`、`failed`、`warning-only`、`argument-error` 等状态 |
| `stage` | string | 当前或失败阶段 |
| `checks[]` | array | 判定项和 issue 摘要 |
| `evidence[]` | array | 输入证据、派生证据和事实来源 |
| `artifacts[]` | array | 结果文件、日志、报告等输出路径 |
| `nextActions[]` | array | 后续动作 |
| `summaryText` | string | 面向人类的短摘要 |

JSON 消费方必须优先读取这些字段，而不是从 stdout 文本推断状态。

## 3. 只读 workflow 字段

以下 workflow 属于只读/维护类结果：

1. `project-health`
2. `release-check`
3. `readonly-sync`
4. `pbl-change-intake`
5. `shared-library-writeback-check`

这些结果除共同字段外，必须提供稳定的 `workspaceModel`。`workspaceModel` 是路径事实、工作区、库、对象、source layout 和 shared-library evidence 的统一来源。PowerShell wrapper、Toolkit skill、SharpIDE 和 CI 不应重新解析 PBW/PBT/PBL 来替代它。

`3.7.1` 起，`pbl-change-intake` 在 success、blocked、failed 路径都必须输出 `workspaceModel`，并把项目模型 evidence 汇总到 `artifacts[]`。实际 `.pbbridge/pbl-change-intake.json` 应能直接通过 `pbbridge contract validate`；缺少 `workspaceModel` 应视为契约漂移。

`3.12.0` 起，`pbl-change-intake` 支持 `--projection-only` 轻量模式。该模式必须配合 `--refresh-library` 或 `--refresh-object-key` 使用，继续复用 `schemaName=pbbridge-v3-pbl-change-intake` / `schemaVersion=3`，并通过 additive 字段输出 `projectionOnly`、`requestedLibraries`、`refreshedLibraries`、`refreshedObjectCount`、`changedSourceFiles`、`deletedSourceFiles`、`staleProjectionCandidates`、`skippedGlobalChecks` 与 `libraryResults[]`。projection-only 只刷新命中 PBL 的文本投影和 manifest/source layout，默认不删除业务源码；确需删除 stale 投影时必须显式传 `--allow-delete-projection`。4.3.0 二次重发后，`--refresh-object-key` 的最终写回范围严格限制为目标对象，旁路对象变化不得写入 `src` 或进入 `changedSourceFiles`。它不自动执行 drift-remediation、verify、report、source-hygiene、baseline refresh、release-check 或仓库级 gate；默认 full intake 路径保持不变。

## 4. 项目模型解释入口

`3.1.0` 新增只读解释入口：

```powershell
pbbridge project model show --project-root . --workspace default
pbbridge project model show --project-root . --compact
```

该命令输出 `schemaName=pbbridge-v3-project-model`，用于给外部项目、Toolkit、CI 和 SharpIDE 展示项目事实，而不要求消费方重新解析 `.pbw/.pbt/.pbl`。结果必须包含：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `workspace` | object | workspace 名称、根目录、输入 PBW 和库/对象计数 |
| `targets[]` | array | target/library 展示摘要 |
| `libraries[]` | array | 正式 `PbLibraryModel` |
| `objects[]` | array | 正式 `PbObjectModel` |
| `sourceLayout` | object | 当前 `beside-pbl-src` 事实 |
| `manifestFacts` | object | manifest 路径、存在性和 source root |
| `sharedLibrarySummary` | object | shared-library role/evidence 摘要 |
| `dependencySummary` | object | self/consumer/conflict 关系摘要 |

如果 manifest、`.pbbridge/shared-libraries.json` 或 shared-library gate evidence 出现角色冲突，命令应输出 `status=blocked` 或 `warning-only`，并通过 `nextActions[]` 给出修复方向，不应静默选择。

当前所有 V3 workflow stdout 都只输出 `schemaName=pbbridge-v3-compact-summary`，并通过 `resultJsonPath` 指向完整 workflow JSON。compact stdout 不是 workflow 事实源，跨 workflow 判断必须读取完整 JSON。

`3.9.0` 起，`import-objects` 提供同一目标 PBL 的多对象批量写回入口。完整 JSON 使用 `schemaName=pbbridge-v3-import-objects`、`schemaVersion=3`，在共同字段之外追加 `objectResults[]`、`pblBatches[]`、聚合 counts、timings、diagnostics bundle 路径和 rollbackPlan；默认 stdout 仍是 compact summary。跨 PBL 对象批量默认 blocked，应拆分命令执行。

`import`、`import-object`、`import-objects` 默认 `--compile-context pbt`，按 PBW/PBT `LibList` 构建写回编译依赖。完整 JSON 包含 `compileContextMode`、`compileContextSource`、`missingCompileDependencies[]`、`haltReason` 和 `nextCommand`。`IncludeLibrary`/`ExcludeLibrary` 只影响 `.sr*` 源码事实源，不应过滤 import 的编译依赖。manifest lookup 在 preflight、Apply 和 post-review 之间使用同一 collision-aware 规则；缺依赖 reason 至少区分 `missing-file`、`path-resolution-mismatch` 和 `unexpected-final-list-omission`；`nextCommand` 使用 PowerShell-safe quoting。

`3.11.0` 起，`import-objects` non-blocked 路径使用固定并行度 worker 限流构造 body diff 与 object fact，并复用已解析的 baseline/current manifest 解析 source path，避免逐对象重复读取 manifest；默认并行度为 `min(Environment.ProcessorCount, 8)`，可通过 `PbImportObjectsRequest.DiffParallelism` 或 CLI `--diff-parallelism <1-32>` 覆盖。完整 JSON 追加 `diffParallelism`，但 `objectKeys[]`、`objectResults[]`、`plan.steps[]` 和 `pblBatches[]` 输出顺序保持稳定。`objectResults[]` 追加 `targetLibraryId`、`targetResolutionSource`，`pblBatches[]` 追加 `targetResolutionSources[]`；解析来源固定为 `target-entry`、`target-library-id`、`source-library-id`、`step-target-pbl-path` 或 `unresolved`。batch hash 对 objectKey 输入顺序和大小写不敏感，文件名前缀仍保留当前命令首个对象短名。`import-objects` 会在主 result 首次写入前预先计算专用 diagnostics bundle 路径，随后写 bundle，避免为了补路径重复写 result JSON；`diagnostics summary` 读取完整 JSON facts 时会输出 target PBL batch 数、unresolved object 数、`diffParallelism`、resolution source 摘要、`targetResolutionSourceCounts` 和推荐后续命令。

`3.7.1` 起，`project model show --compact` 只缩短 stdout，输出 `schemaName=pbbridge-v3-compact-summary`、原始 workflow schemaName、状态、摘要计数、证据路径、`nextActions[]` 和完整 JSON 路径；完整 `pbbridge-v3-project-model` 仍写入 `--result` 或默认 `.pbbridge/project-model.json`。

## 5. 3.2.0 只读体验 workflow

`3.2.0` 新增两个 additive workflow，不改变 v3 共同字段，不引入 v4 schema。

```powershell
pbbridge project adoption check --project-root .
pbbridge project adoption check --project-root . --compact
pbbridge diagnostics summary --project-root .
```

`project adoption check` 输出 `schemaName=pbbridge-v3-project-adoption-check`，用于外部项目接入自检。它只读检查 Toolkit runtime、CLI/Toolkit/template 版本、wrapper 现状、`.pbbridge/workspaces` Git 跟踪风险、manifest/source layout 和 shared-library evidence；输出 `toolkitRuntime`、`versionAlignment`、`workspaceTracking`、`adoptionPlan` 和 `workspaceModel`。该入口只给诊断、建议或可审计同步计划，不静默覆盖外部项目本地自定义文件。

`3.7.1` 起，`project adoption check --compact` 同样只缩短 stdout，完整 `pbbridge-v3-project-adoption-check` 仍写入 `--result` 或默认 `.pbbridge/project-adoption-check.json`。

当前可通过 `--profile standalone|shared-library-self|shared-library-consumer|pb9` 固定外部项目接入口径。profile 只影响诊断和建议，字段为 `adoptionProfile`、`profileChecks[]` 和 `profileEvidence[]`；shared-library self/consumer 必须消费项目模型和 shared-library evidence，不由 wrapper 重新推导规则。

`3.5.0` 起可显式生成或引用 adoption baseline：

```powershell
pbbridge project adoption check --project-root . --profile standalone --write-baseline
pbbridge project drift check --project-root .
pbbridge project model diff --project-root .
```

baseline 默认路径为 `.pbbridge/adoption-baseline.json`，只用于诊断、比较和建议。`project drift check` 输出 `schemaName=pbbridge-v3-project-drift-check`，包含 `driftStatus`、`driftItems[]`、`baseline`、`current`、`checks[]`、`evidence[]`、`artifacts[]` 和 `nextActions[]`。drift 分级为 `info`、`warning`、`blocked`；shared-library role/evidence 冲突必须 warning 或 blocked，不静默选择。

`diagnostics summary` 输出 `schemaName=pbbridge-v3-diagnostics-summary`，聚合 project-health、release-check、readonly-sync、project-model、contract validate 和 release engineering summary 等 CLI/Core JSON facts，并输出 `conclusions[]`：是否可继续修改、是否可 DryRun、是否可 Apply、是否可提交、是否可发布。结论只从 JSON facts 推导，不从 stdout 文本猜测。

`3.7.0` 起，`diagnostics summary` 支持快路径：

```powershell
pbbridge diagnostics summary --project-root . --run-missing
pbbridge toolkit preflight --project-root .
```

`--run-missing` 会先读取已有 workflow JSON facts，只在缺失时按需生成 project model / project adoption check 等只读 facts，并把生成的文件写入 `artifacts[]` 或 `evidence[]`。`toolkit preflight` 输出 `schemaName=pbbridge-v3-toolkit-preflight`，在同一 CLI 进程内聚合 Toolkit runtime cache、workspace model cache 和 diagnostics summary；PowerShell wrapper 仍只透传 JSON 与退出码，不解析 PBW/PBT/PBL，不实现 shared-library gate 或写回阻断规则。

`3.7.2` 起，完整 `readonly-sync --compact`、`readonly-sync --summary-only --compact` 和 `pbl change-intake --compact` 用于大型项目日常日志降噪；它们只输出摘要计数和完整结果路径，stdout 不包含完整 `workspaceModel`，完整 `pbbridge-v3-readonly-sync`、`pbbridge-v3-readonly-sync-summary` 或 `pbbridge-v3-pbl-change-intake` 仍写入结果文件。`readonly-sync status=blocked` 固定返回 exit `10`，包括 compact stdout 路径。`diagnostics summary --run-missing` 继续读取完整 JSON facts，不从 compact stdout 推断。

`3.7.3` 起，`diagnostics summary --compact`、`release check --compact` 和 `project health --compact` 也输出 `pbbridge-v3-compact-summary`；compact stdout 不输出完整 `workspaceModel`、长 `inputs`、长 `checks/issues/files` 清单，完整 `pbbridge-v3-diagnostics-summary`、`pbbridge-v3-release-check` 和 `pbbridge-v3-project-health` 仍写入结果文件。`source-hygiene` 结果新增 `reasonSummary[]`、`actionSummary[]` 和文件级 `hasTrailingWhitespace`；diagnostics summary 新增可选 `recommendedNextCommand`，用于在 PBV076、缺失 readonly facts、缺失 release/adoption/project facts 等场景提示最短下一命令。这些字段都是 additive，不改变 v3 共同字段语义。

`7.2.2` 起，readonly-sync 按“显式 `--source-hygiene-policy`、项目根默认策略、不存在则 disabled”解析卫生策略，并在完整结果中记录策略来源、规范路径、SHA-256、规则数和 accepted 数。显式策略缺失或无效分别返回 `SOURCE_HYGIENE_POLICY_NOT_FOUND`、`SOURCE_HYGIENE_POLICY_INVALID`。同版本在 `pbbridge-v3-project-health` schemaVersion 3 中兼容性增加 `acceptanceSummary`，compact 追加 `acceptanceVerdict`；旧 `status`、`blocked`、`decision` 与退出码不变。

`7.2.3` 起，readonly-sync 的格式噪声检查按当前 workspace 源码的只读 repository graph 聚合，并兼容性增加 `formatNoiseRepositories[]`。source-hygiene full/compact 增加 `performanceSummary` 和 `repositorySummary[]`；每仓库使用一次 index 枚举和一个 `git cat-file --batch` 会话。任一应检查仓库不可读取时 `formatNoise=incomplete`，不得误报 `none`；这些字段不改变 project-health schemaVersion 3 或共享库写回授权。

`3.11.0` 起，`diagnostics summary` 会识别 `pbbridge-v3-import-objects` 完整 JSON，基于 `objectResults[]`、`pblBatches[]` 和 `diffParallelism` 生成 `importObjectsTargetResolution` 结论；结论 reasons 包含 target batch 数、unresolved object 数、resolution source 集合、source counts 和实际 diff 并行度。它只消费 CLI/Core JSON facts，不解析 compact stdout，也不重新解析 PBW/PBT/PBL。

`3.7.4` 起，模板迁移报告对受管 wrapper 的项目默认参数差异输出更精确的分类。纯 PBW、workspace、scan scope、include/exclude library、PBL baseline 等参数差异归类为 `project-configuration`；如果同时存在模板主体差异，报告继续保留模板漂移结论，并通过 additive `projectConfigurationDiffs[]` 标出应保留的项目参数。

常见诊断汇总用法：

```powershell
pbbridge diagnostics summary --project-root . `
  --input .\.pbbridge\project-health.json `
  --input .\.pbbridge\release-check.json `
  --input .\.pbbridge\project-model.json `
  --output .\.pbbridge\diagnostics-summary.json
```

如果省略 `--input`，命令会按项目根目录下的标准 `.pbbridge` 位置寻找已存在的 CLI/Core JSON facts；如果指定 `--output`，结果固定落盘到该路径，便于 CI、Toolkit skill、SharpIDE 只读 facade 或外部 agent 交接。

`3.3.0` 新增证据交接入口：

```powershell
pbbridge diagnostics bundle create --project-root . `
  --input .\.pbbridge\project-health.json `
  --input .\.pbbridge\diagnostics-summary.json
```

`diagnostics bundle create` 输出 `schemaName=pbbridge-v3-diagnostics-bundle`，包含 `bundleManifest`、`facts[]`、`gitSummary`、`sha256[]`、`checks[]`、`evidence[]`、`artifacts[]` 和 `nextActions[]`。bundle 用于跨外部项目、CI、Toolkit skill、SharpIDE 只读 facade 和人工发布交接；不得包含敏感信息、大量 `.pbbridge/workspaces` 临时内容，必须对本机路径标注 local-only evidence。

`3.5.0` 起可验证 bundle 完整性：

```powershell
pbbridge diagnostics bundle verify --project-root .
pbbridge diagnostics bundle verify .\.pbbridge\diagnostics-bundle.json
```

`diagnostics bundle verify` 输出 `schemaName=pbbridge-v3-diagnostics-bundle-verify`，包含 `bundleManifest`、`sha256[]`、`redactionSummary`、`checks[]`、`evidence[]`、`artifacts[]` 和 `nextActions[]`。

`3.6.0` 起，CLI 内部以轻量 command descriptor 收敛命令事实源。descriptor 只描述命令名、workflow、`schemaName`、help 摘要、分组命令 normalization 和 contract route coverage；它不改变任何 v3 JSON 字段。新增 workflow 时，应同时更新 descriptor、workflow registry、`schema show`、`contract validate` 和 contract tests，避免 route/help/schemaName 漂移。

`3.6.0` 起，CLI/Core 内部以轻量 evidence envelope/reference 术语统一说明证据边界：

| 术语 | 含义 |
| --- | --- |
| `workflowFact` | 单个 v3 workflow JSON 或其摘要 |
| `handoffBundle` | `diagnostics bundle create/verify` 产物 |
| `releaseProvenance` | release engineering summary 中的发布来源事实 |
| `releaseAssetHandoff` | 发布资产交接检查事实 |
| `localOnlyEvidence` | 只能在本机解释的路径或证据 |
| `legacyImportDiagnostics` | import/writeback 旧 pipeline 中的 diagnostics bundle 兼容事实 |

这些术语不改变现有 v3 JSON 字段；它们用于文档、测试、diagnostics bundle manifest 和外部 agent 交接说明。消费方仍必须读取 CLI/Core JSON facts，不应解析 stdout 文本或重新实现项目模型/写回阻断规则。

## 6. import / writeback workflow 字段

以下 workflow 属于 import/writeback 状态机结果：

1. `import`
2. `import-object`
3. `import-package`
4. `confirm-object-writeback`

这些结果除共同字段外，必须提供：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `workspaceModel` | object | 当前工作区统一事实 |
| `applySessionId` | string | 本次 apply/writeback 会话标识 |
| `stages[]` | array | 标准阶段投影 |
| `rollbackPlan` | object | 可恢复范围、回滚证据和人工动作 |

标准阶段顺序为：

```text
plan -> dryrun -> apply -> writeback -> post-apply-review -> re-export -> verify
```

`confirm-object-writeback` 是只读确认 workflow，也必须用同一阶段语言表达 skipped/succeeded/failed，并在 `rollbackPlan` 中说明未修改文件时不需要 rollback。

3.1.0 起，`stages[].failureCategory` 使用稳定分类：`argument-error`、`preflight-blocked`、`verify-blocked`、`shared-library-blocked`、`import-conflict`、`adapter-failure`、`writeback-failure`、`post-apply-review-failed`、`re-export-failed`、`rollback-required`、`ide-intervention-required` 或 `none`。wrapper 不应自定义新的分类。

`3.5.0` 起新增只读写回准入检查：

```powershell
pbbridge writeback readiness check --project-root .
```

该命令输出 `schemaName=pbbridge-v3-writeback-readiness-check`，包含 `readinessStatus`、`eligibleStages[]`、`blockedStages[]`、`failureCategory`、`workspaceModel`、`checks[]`、`evidence[]`、`artifacts[]`、`nextActions[]` 和 `rollbackPlan`。它只评估前置条件，不新增写回 adapter，不改变支持矩阵。

## 7. 错误 JSON

参数错误或执行失败必须输出结构化错误 JSON：

1. `schemaName=pbbridge-v3-error`
2. `schemaVersion=3`
3. `status=argument-error` 或 `status=failed`
4. 包含 `checks[]` 和 `nextActions[]`

消费方不应只依赖进程 stderr 判断失败原因。

## 8. 退出码

v3 基础退出码固定为：

| 退出码 | 含义 |
| --- | --- |
| `0` | success |
| `1` | execution-failed |
| `2` | argument-error |
| `10` | blocked |
| `11` | warning-only |

`exit 10` 表示业务阻断，不等同于脚本崩溃。`AllowBlockedResult` 或 `--allow-blocked-result` 只表示保留 blocked JSON，不能把 blocked 改写成 success。

## 10. 发布工程 JSON 摘要

`scripts/build-release-engineering.ps1` 会在发布校验中输出 `artifacts/release/<version>/checks/release-engineering-summary.json`，其 `schemaName=pbbridge-v3-release-engineering-summary`。摘要包含 `version`、`commit`、`tag`、`toolkitCommit`、`toolkitVersion`、`cliVersion`、`releaseArtifacts`、`checks`、`status` 和 `nextActions`。

`3.2.0` 起摘要还包含 `releaseAssetHandoff` 和 `releaseNotesSummary`。前者检查 release manifest、VERSION、Toolkit manifest、CLI version、tag 是否指向 HEAD、Toolkit commit 是否可由远端分支追溯；后者生成 `release-notes-summary.md`，供人工发布页或内部发布记录使用。

`3.3.0` 起摘要还包含 `releaseProvenance`，记录 `version`、`commit`、`tag`、`tagCommit`、`toolkitCommit`、`toolkitVersion`、`cliVersion`、`releaseManifest`、`SHA256SUMS`、runtime contract、`releaseArtifacts[]`、`checks[]`、`status` 和 `nextActions[]`。release/tag guard 会剥离 annotated tag object 后比较实际 commit，避免把 annotated tag 误判为未指向 HEAD。

`7.2.0` 起摘要中的 `runtimeBenchmark` 只消费 schemaVersion 2。small/real 仍是 smoke 或 warning-only；medium/large 合成证据缺失、绝对预算超限或相对回归越过 20% 且绝对增量超过 10ms 时阻断发布，内存和吞吐首版只产生趋势 warning。

发布脚本会先执行 release/tag guard：目标 tag 已存在但不指向当前 HEAD 时默认 `blocked`，不会静默移动已推送 tag。只有显式传入 `-AllowPublishedTagMove` 才允许继续，并且结果会降为 `warning-only` 语义。

## 11. 消费边界

1. Toolkit 和 PowerShell wrapper 只负责 CLI 调用、路径适配、日志落盘和 JSON/退出码透传。
2. SharpIDE 只消费 CLI/Core JSON，不承载 PBW/PBT/PBL、shared-library gate 或写回阻断业务规则。
3. `source-hygiene.json` 不能单独解释 `.pbl` drift。
4. Apply 成功不等于 PowerBuilder IDE Regenerate、Full Build 或业务运行验收通过。
5. ORCA 仍是 candidate，不是默认或正式 supported PBL 写回器。
