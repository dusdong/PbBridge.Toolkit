# 第一次完成一次业务变更

从一个明确的业务目标和最小对象范围开始。这条路线面向 7.7.0 Windows Toolkit 的 V8 delivery；写回完成、PB IDE 编译通过和业务验收是分别记录的结果。下载与未验证范围见发布说明（父仓 `docs/使用手册/93-7.7.0发布说明.md`，不随包分发）。

## 1. 在业务项目中安装并接入

按[安装与升级](安装与升级说明.md)校验并放置完整 Toolkit，再按[项目接入](外部PowerBuilder项目接入Codex.md)配置项目根目录、workspace、PBW/PBT 和源码映射。可观察结果是项目配置能明确指向本次目标 PBL、对象键和 `.sr*` 源码，而不是靠隐式发现猜选 workspace。

缺件、身份不一致或映射不清时，先按安装/接入指南修正；不要只换 CLI。已有项目升级走安装指南的 Plan、定制审阅、授权 Apply、Plan no-change，再对每个 workspace 做 upgrade-check 和新预检；旧 session 只供历史查询。准备好后进入下一步。

## 2. 修改最小源码范围，预检并审阅真实结果

在业务项目根目录按[快速开始](快速开始.md)运行 doctor，再用[协作模板的预检段](../workflows/PbBridge.Cli协作模板.md#1-预检与审阅)生成 V8 preflight。读取 stdout 指向的完整结果，核对 workspace、PBL/对象与源码、session、可执行性、阻塞原因和下一动作；保存真实结果路径。doctor 健康或预检通过都不表示已经写入或完成 IDE 验收。

遇到语法或编译错误，在既有授权内最小修正，再生成新预检并使用新结果；源码、依赖或环境没有变化时不要原样循环 Apply。实际文件锁、目标漂移、冲突或恢复责任按 CLI 的具体结果处理；只在确需用户决策或 IDE 动作时暂停依赖步骤。诊断可查[原始源码定位](../reference/编译诊断到原始源码定位.md)，无法解决时保留 reason code 并使用[反馈模板](../reference/Toolkit问题反馈模板.md)。审阅允许继续后再核对写回授权。

## 3. 执行当前任务已授权的写回

确认目标范围符合当前任务授权，且实际预检允许继续，才使用[独立写回段](../workflows/PbBridge.Cli协作模板.md#2-确认授权后写回)从该预检 continue。CLI 会再检查事实新鲜度；不要改 JSON 或绕过门禁。输出应能观察到实际成功对象、post-apply review、promotion/recovery 状态和原 session，不以命令退出代替实际写回结果。

失败时保留实际结果和已有成功对象，按返回的下一动作处理。需要恢复时只使用绑定的 promotion intent，无法在授权内解决则停止依赖写回并交接。修复后重新预检；用新结果对应的 session 继续，不把旧成功转成当前资格。写回后进入人工交接。

## 4. 给 PB IDE 交接，收到实际结果后回填

需要人工时，先按[交接与证据段](../workflows/PbBridge.Cli协作模板.md#3-先交接再登记实际证据)对本次写回的同一 session 生成 handoff：明确 workspace/PBW、PBL/对象、操作步骤、未完成项和所需日志/场景结果。由用户在 PB IDE 完成适用的 Regenerate、Full Build、运行和业务验收；不要让 AI 自动操控 IDE。

没有实际证据的项目保持 `not-checked`，已知失败继续保留。收到结果后核对 session、操作对象及验收范围，再按适用情况 ingest 日志或 attest 人工结果，并刷新同一 session 的 handoff。人工通过是 `attested`，不能报告为 `verified`；图片证据可能仍待审阅。失败就记录失败并给出下一步，缺少结果就交接待办，不预填成功。

最后按[业务变更交付视图](../reference/业务变更交付视图.md)查看本次对象及 session：分别报告最近尝试、已核验写回和剩余验收；多 session 不会自动合成发布就绪。功能和现场适用性见边界说明（父仓 `docs/使用手册/32-功能边界与适用范围.md`，不随包分发）。
